# AGENTS.md

This file provides guidance to AI coding agents (Claude Code, Codex, etc.) when working with code in this repository. `CLAUDE.md` imports this file, so edit here rather than there.

## Running the app

```bash
source ~/venv/bin/activate
pip install -r requirements.txt
python serve.py          # serves at http://127.0.0.1:8765/
```

To regenerate `dashboard.html` without starting the server:

```bash
python build_dashboard.py
```

To run the test suite (no dependencies beyond the project itself; network calls are faked):

```bash
python test_merge_dedup.py       # live/export dedup
python test_artist_sessions.py   # Artist web session splitting
python test_cloud_pull.py        # pull_exports() only downloads missing exports
python test_art_sync.py          # art search misses are remembered, not retried
python test_lastfm.py            # Last.fm tag cleanup and fetch flow (faked Last.fm)
python test_genres.py            # one genre per artist from Last.fm tags
```

Spotify refresh requires a Spotify app Client ID. Set it in `.env`:

```
SPOTIFY_CLIENT_ID=your_client_id_here
```

Create the app at https://developer.spotify.com/dashboard and add `http://127.0.0.1:8765/callback` as the redirect URI with the Web API checkbox enabled.

`serve.py` also respects `REFRESH_BIND_HOST` (default `127.0.0.1`) and `REFRESH_PORT` (default `8765`) env vars.

For cloud sync, also set in `.env`:

```
DATA_REPO=yourname/spotify-analysis-data
DATA_REPO_TOKEN=your_github_pat
```

`DATA_REPO_TOKEN` needs **Contents: Read and write** permission — it's used both to pull and to push the live buffer back after a local refresh.

For the Taste River's artist tags, also set a read-only Last.fm API key (https://www.last.fm/api/account/create, callback URL blank) and fill the cache once:

```
LASTFM_API_KEY=your_key
python lastfm_sync.py    # ~2 requests per top-400 artist, ~3 min; later Rescrapes top up 25 stale artists
```

## Architecture

Eight Python modules, no database — all state lives in local JSON files.

**`build_dashboard.py`** — data pipeline. Reads all `music-history/Streaming_History_Audio_*.json` files, computes aggregate statistics (per-day/month/year series, top artists/tracks/albums, heatmap, streak, etc.), serializes the result to a JSON bundle, then injects it into `template.html` by replacing the `__DATA_JSON__` placeholder string. Output is `dashboard.html`. This file is auto-rebuilt by `serve.py` whenever source JSON or `template.html` is newer. Also emits `artist_sessions` for the Artist web (see Key conventions).

**`spotify_sync.py`** — Spotify API layer. Implements PKCE OAuth (no client secret), fetches the 50 most recently played tracks via `/v1/me/player/recently-played`, maps them to Extended Streaming History-shaped rows, deduplicates by `(ts, spotify_track_uri)` key, and atomically appends new rows to `Streaming_History_Audio_live.json`. Credentials are read from `.env` (`SPOTIFY_CLIENT_ID`) or `spotify_config.json`. Tokens are cached in `spotify_tokens.json` (chmod 600, atomic write).

**`art_sync.py`** — Fetches real Spotify album art and artist photos for the current top 12 albums/tracks and top 80 artists (by minutes played), for the Rankings podium, the Artist web, and the Top listens race. Uses `/v1/search` (name + artist query) rather than direct id lookups — `/v1/tracks` and `/v1/artists` return 403 under this app's current Spotify API access tier, but Search remains available and returns the same image data. Search's top hit is unreliable (e.g. "aespa" → IVE), so `_search()` fetches 10 results and caches only one whose artist name matches exactly. Reuses `spotify_sync.ensure_access_token()` for auth. Caches results to `art_cache.json` (gitignored), keyed `artist:<lowercased name>` / `album:<canon_album_key>` / `track:<canon_track_key>`. Best-effort like `cloud_pull.py`: failures are logged and returned as `(False, msg)`, never raised, so a refresh never breaks because art couldn't be fetched.

**`lastfm_sync.py`** — Fetches Last.fm `artist.getTopTags` and `artist.getSimilar` for the top `GRAPH_ARTIST_CAP` (400) artists by minutes and caches them in `lastfm_cache.json` (gitignored), keyed `artist:<lowercased name>` → `{name, tags, similar: [[name, match], ...], fetched}`. Only an API key is needed (`LASTFM_API_KEY`), no login flow. Tags are cleaned by `clean_tags()` (blacklisted generic tags, bare years and the artist's own name dropped; top `MAX_TAGS` (5) with weight ≥ `MIN_TAG_COUNT` (20)). Entries refresh after 30 days; unknown artists get an empty entry so they aren't re-requested. Requests go through 4 threads behind a shared ~5 req/s limiter. `python lastfm_sync.py` fills everything; Rescrape fetches at most `BATCH_LIMIT` (25) missing/stale artists. `build_dashboard.py` reads the cache read-only via `load_lastfm_cache()` and attaches `tags` to each artist entry that has them; `build_lastfm_links()` turns the similar lists into `DATA.lastfm_links` (`[i, j, match]`, indices into `DATA.graph_artists`, stronger direction wins), used by the Artist web's Similar artists mode, the Taste Map layout, and `genres.py`'s neighbour fallback. Best-effort like `art_sync.py`: returns `(False, msg)` and never raises; skipped when `LASTFM_API_KEY` is unset.

**`genres.py`** — Pure functions (no I/O, tested by `test_genres.py`) that give each artist one genre for the Taste River. `assign_genres(tags, minutes, links)` merges tag spellings and synonyms into families (`FAMILIES`: kpop / k-pop / korean → "k-pop", lofi / chillhop → "lo-fi", etc.), prefers the most specific qualifying genre over umbrella tags (`GENERIC`: pop, rock, electronic, japanese, …), only keeps genres with at least `min_artists` (12) artists (an artist whose genre is too small falls back to its next tag), and lets untagged artists borrow the weighted majority genre of their Last.fm-similar neighbours (marked `gi: 1`). `build_dashboard.py` runs it over the top `GRAPH_ARTIST_CAP` (400) artists and stores `DATA.genres` (names ordered by total minutes) plus each artist's index in `g`; artists outside the top 400 have no `g`.

**`serve.py`** — Flask server. Every rebuild goes through `rebuild_dashboard()`, which `importlib.reload`s `build_dashboard` first so a long-running server never builds with stale code (edits to `serve.py` itself, `art_sync.py`, etc. still need a server restart). On startup it exits with an error if something already accepts connections on `HOST:PORT`, so duplicate servers can't share requests. Routes:
- `GET /` — serves `dashboard.html`, triggering a rebuild if stale
- `GET /callback` — receives the OAuth code from Spotify and puts it on `oauth_code_queue`
- `POST /api/pull` — pulls any missing yearly exports and then the live buffer from the data repo (if configured), then rebuilds the dashboard. Does NOT call the Spotify API. Triggered by the "Refresh" button.
- `POST /api/refresh` — always runs `cloud_pull.pull_exports()` and `cloud_pull.pull_live()` (if configured), then `spotify_sync.sync_incremental()`, then `art_sync.refresh_art_cache()`, then `lastfm_sync.refresh_cache()`, then `rebuild_dashboard()`, then `cloud_pull.push_live()` (if configured), under a combined threading lock + PID-based file lock (`.refresh.lock`). Operates locally even without cloud credentials. Triggered by the "Rescrape" button.
- `POST /api/authorize` — forces a fresh Spotify PKCE login, stores the new refresh token locally, and pushes it to the data repo. Triggered by the "Re-authorize" button.
- `GET /api/refresh/status` — reads `.refresh.last.json` for last refresh result

**`template.html`** — HTML shell for the dashboard. References `dashboard.js` and `dashboard.css` via `<script src>` / `<link rel>` tags. `build_dashboard.py` injects only the `__DATA_JSON__` blob; charting logic lives in the external JS/CSS files, which Flask serves via `/dashboard.js` and `/dashboard.css` routes. Chart.js and d3 (v7, used only by the Taste River, Artist web and Taste Map layout) are loaded from CDN at runtime (`cdn.jsdelivr.net`) with Subresource Integrity (`integrity="sha384-…"` + `crossorigin`), so changing either version means recomputing its hash. Only reference files that exist in the npm package: jsDelivr generates missing `.min.js` variants on the fly (Chart.js 4.4.1 ships `chart.umd.js`, already minified, but no `chart.umd.min.js`), and a generated file's bytes can change and break SRI. All other charting logic is local.

**`dashboard.js`** — All client-side rendering. Reads `DATA` from a `<script id="dash-data">` tag injected by `build_dashboard.py`. Day-offset arithmetic mirrors the Python bundle: `dayStrToOff` converts calendar dates to integer offsets from `DAY_EPOCH`, so JS and Python indexes stay in sync. Builds Chart.js charts for day/month/year series, heatmap, platform breakdown, and top artists/tracks/albums with a shared date-range filter, plus the hand-drawn canvas "Top Listens Over Time" race, the d3 Taste River, the SVG Daily Heatmap, the d3 Artist web and the canvas Taste Map.

**`dashboard.css`** — All styling for the dashboard.

**`cloud_pull.py`** — Four functions: `pull_live()` pulls the live JSON buffer from the private data repo (GitHub Contents API, with fallback to Git Data API for files >1 MB) into `music-history/Streaming_History_Audio_live.json`; `pull_exports()` downloads yearly `Streaming_History_Audio_*.json` exports from the data repo's top level that are **missing locally** — it never replaces an existing local file, even if the repo's copy differs, since exports are read-only and local copies are authoritative (useful for other users / machines that keep exports in their data repo; a repo holding only the live buffer makes it a no-op); `push_live()` writes the updated buffer back to the data repo after a local sync (uses Git Data API blob/tree/commit to handle files >1 MB); `push_live_token()` rotates the `live_token.json` in the data repo after a token refresh. `push_live()` and `pull_exports()` use the Git Data API, which needs a branch name, so they ask GitHub for the repo's default branch once per process (`default_branch()`, cached in `_branch_cache`) and fall back to `main` if that lookup fails; `pull_live()` and `push_live_token()` use the Contents API, which already targets the default branch, as does the Actions checkout. All are best-effort: if `DATA_REPO` / `DATA_REPO_TOKEN` are unset or the call fails, they log a warning and return `(False, msg)` without raising.

**`cloud_sync.py`** — Headless orchestrator for the GitHub Actions hourly scrape. Reads the Spotify refresh token from the data-repo checkout (`live_token.json`), calls `spotify_sync` to fetch new plays, and writes the updated live buffer and rotated token back so the workflow can commit them atomically. Env vars: `SPOTIFY_CLIENT_ID`, `SPOTIFY_HISTORY_DIR` (path to the data-repo checkout). Exit code 1 means the refresh token is expired and needs re-authorization locally.

## Key conventions

- **Display timezone**: `DISPLAY_TZ = ZoneInfo("America/Chicago")` in `build_dashboard.py`. All user-facing day/month/year buckets and the heatmap use this zone, not UTC.
- **Track/album deduplication**: `canon_track_key` and `canon_album_key` normalize to lowercase and join with `\x01` as separator, collapsing duplicate Spotify URIs for the same title+artist.
- **Extended history JSON vs. live JSON**: All `Streaming_History_Audio_*.json` files live in `music-history/`. Year-based export files are read-only; only `Streaming_History_Audio_live.json` is written by `spotify_sync.py`. The export files are authoritative for any period they cover — `load_events()` drops live rows whose timestamps fall within the export coverage window (plus a 4-second buffer) before running dedup. This prevents double-counting: Spotify's recently-played API reports `played_at` 0–3 seconds later than the data export records the same play, so exact `(ts, uri)` dedup fails to merge them.
- **Day index compression**: `build_dashboard.py` encodes the global `day_series` as `{"i": <days_since_epoch>, "ms": ..., "n": ...}` where the epoch is the calendar date of the first ever play. Per-entity daily data (artists/tracks/albums) uses `compact_days()`, which encodes as `[[i, ms, n], ...]` (3-element lists). JS's `dayOffFromSeriesRow` handles both formats transparently.
- **`is_music_stream()` filter**: Rows with `spotify_episode_uri` (podcasts) or `audiobook_uri` are excluded from all stats. Export JSONs can contain mixed content despite the "Audio" filename.
- **No per-entity data caps**: Every artist, track, and album gets its per-day array included in the bundle (previously capped at the top 2500/2600/1400 by `ms_played`; the caps were removed since they made the "in window" KPI tiles undercount on large histories).
- **Live row `ms_played` resolution**: The Spotify recently-played API returns track duration, not actual listening time. `resolve_live_ms_played()` post-processes unresolved rows (those with `ms_played_resolved: false`) by computing the time delta between consecutive `played_at` timestamps, capped at track duration. Rows already resolved (`ms_played_resolved: true`) are used as reference points but are not modified. This runs automatically after every sync.
- **Background automation (macOS)**: `com.USERNAME.spotify-serve.plist` in the repo root is a launchd agent that keeps the Flask server running. Replace `USERNAME` with your macOS username and load it into `~/Library/LaunchAgents/`. There is no longer a local hourly refresh plist — cloud-side scraping is handled entirely by the GitHub Actions workflow triggered by cron-job.org.
- **GitHub Actions**: `.github/workflows/spotify-sync.yml` runs `cloud_sync.py` on `workflow_dispatch` only — triggered hourly by cron-job.org via the GitHub API (`POST /repos/warithr621/spotify-analysis/actions/workflows/spotify-sync.yml/dispatches`). The cron-job.org PAT needs **Actions: Read and write** on `spotify-analysis` only. There is no keepalive workflow: GitHub's 60-day auto-disable only applies to `schedule` triggers, which this workflow doesn't use. Required secrets: `SPOTIFY_CLIENT_ID`, `DATA_REPO_PAT` (Contents: Read and write on `spotify-analysis-data`). Required var: `DATA_REPO`. Optional var: `SPOTIFY_AUTH_DATE` (YYYY-MM-DD of last local re-auth, used to warn when the token nears 180-day expiry).
- **Stale rebuild trigger**: `maybe_rebuild_dashboard()` in `serve.py` compares `dashboard.html` mtime against `template.html`, the `music-history/Streaming_History_Audio_*.json` files, `build_dashboard.py`, `art_cache.json`, and `lastfm_cache.json` (skipped when absent) — rebuilds automatically on `GET /` if any source is newer.
- **API coverage limit**: `spotify_sync.py` fetches from `/v1/me/player/recently-played` with a cursor-based `after` parameter. The API window is ~50 items per page and covers roughly the last 50 plays Spotify has synced. Offline plays appear only after the device reconnects and syncs to Spotify's servers; if many plays accumulated while offline, plays outside the API window may be missed and must come from a Spotify Extended Streaming History export.
- **Rankings layout**: The Rankings section renders three full-width cards (Artists/Albums/Tracks), each a stepped 2nd/1st/3rd podium (top 3, with art) above a scrollable compact list (rank 4+, no art, sticky header). Columns differ by category but are always exactly 3 data fields beside the rank number — Artists: Name/Streams/Minutes; Albums: Album/Artist/Minutes; Tracks: Track/Artist/Minutes. Every minutes figure (podium and list) carries a muted second line from `minutesHint()`: artists show the `fmtMin` day/hour conversion (their streams already have a column / podium row), while albums and tracks show their stream count (`streamsLabel()`, "1 stream" / "N streams"). Rendered by `renderRankSection()` in `dashboard.js`; the search box filters by toggling element visibility (`applySearchVisibility()`) rather than rebuilding the DOM or re-ranking.
- **Minutes only**: everything ranks and sizes by minutes listened (`fm`). There used to be a Minutes/Plays switch; it was removed as unused, so `rankArtists`/`rankTracks`/`rankAlbums` always sort by minutes. Play counts (`fn`) are still computed and shown as streams in Rankings.
- **Art cache**: `art_cache.json` (gitignored, like `dashboard.html`) maps `artist:<name>` / `album:<key>` / `track:<key>` to a Spotify CDN image URL, plus `miss:<same key>` → ISO date for searches that found no verified match. Populated by `art_sync.py` (see Architecture); `build_dashboard.py` reads it read-only via `load_art_cache()` and attaches an `image` field to each artist/track/album entry in the bundle when cached. Entities without cached art fall back to a colored initial-letter tile in the frontend (`artHtml()` in `dashboard.js`). `art_sync.py` fetches the top `TOP_N = 12` tracks/albums and the top `ARTIST_TOP_N = 80` artists (enough for the Artist web's "Top 75" setting), so most tracks/albums in the race have no art of their own; the race falls back from track/album art to the artist's photo before the initial-letter tile. A search with no verified match (or a match with no images) is recorded as a `miss:` entry and not retried for `MISS_RETRY_AFTER` (30 days); a later hit replaces it. Request errors are not recorded, so transient failures retry on the next Rescrape. `build_dashboard.py` only looks up `artist:`/`album:`/`track:` keys, so misses never appear as images.
- **Top listens race** (third card in the Trends section, `race*` functions in `dashboard.js`): hand-drawn canvas line chart animated over the shared date range. Each line is one artist/track/album; its value on a given day is minutes in a trailing 7- or 30-day window, or a running total for "All time" — which is seeded with all listening *before* the selected range, so narrowing the dates doesn't reset it. `buildRaceData()` builds dense per-day arrays for a candidate pool (`RACE_POOL`: top 400 artists / 700 albums / 1500 tracks by all-time minutes) and marks each day's top `RACE_TOP` (10) as shown; each line's per-day opacity is its share of the last `RACE_FADE_DAYS` (4) days in that top list, so lines and their end labels fade in and out instead of popping.
  - **Controls** are one row of labeled button groups (`.seg[data-race]`, wired generically in `wireRaceControls()`; `data-race` names the `race` setting, `data-v` its value): Rank (artists/tracks/albums), Counted over (7 days / 30 days / all time; default 30), View (3 months / 1 year / all; default 1 year), plus Play/Pause/Replay. There is no speed control: the whole playable range always takes `RACE_PLAY_SECONDS` (22 s). There is no artist filter or Restart button (both removed as unused).
  - **Behavior**: rests on the latest day until Play is pressed (no autoplay); Replay restarts from the first listen. `renderRace()` rebuilds on date-range change (from `renderCharts()`); kind/trail changes go through `raceRebuild()`, which keeps the playhead; a View change only redraws.
  - **Drawing**: colours come from the page's CSS tokens (`raceColors()`, light theme); each entity's line colour is a hash of its id (`raceColorOf()`), so it never changes with settings. Tracks/albums are labeled "Title · Artist" (`by` on the entity; the title is shortened first). Vertical date lines sit on calendar boundaries (monthly / quarterly / yearly by view length), and the only text inside the plot besides tick labels and end labels is the big current date plus the axis titles: "Date" under the x-axis, and a rotated y-axis title that follows Counted over ("Minutes listened, last 7/30 days" or "Total minutes listened").
- **Taste River** (`#river-card`, last card in the Trends section, `renderRiver()`): d3 streamgraph (wiggle offset, inside-out order) of genres by minutes over the shared date range: Top 12 / Top 24 / All (`.seg` `#river-count`, default Top 12; a Top N button is disabled when the range has fewer than N genres, and a disabled selection falls back to All). Monthly buckets for ranges over ~8 months, weekly otherwise; partial edge buckets are trimmed, and ranges under two weeks show a message instead. A faint vertical line (`.river-year`) marks every January 1st, drawn behind the streams like the race's date lines. Each artist counts toward exactly one genre (`DATA.genres[a.g]`, from `genres.py`), so streams never overlap and artists without a genre (including everyone outside the top 400) are left out. The heading reads "Taste River: N Genres Plotted" (`#river-title`, the number of streams drawn; plain "Taste River" when nothing is drawn). Colours are keyed to the genre's all-time rank, so they don't change with the date range. Hidden entirely when there are no genres (no `LASTFM_API_KEY` / empty cache). Styled for the light theme like the race (`.river-host`); tooltips are positioned by `placeTip()`.
- **Daily Heatmap** (`#heatmap` section, between Trends and Artist Dive; `renderHeatmap()` / `wireHeatmap()`): GitHub-style SVG calendar of **one year at a time**, picked with `‹ year ›` arrows (`#heat-prev` / `#heat-next`, `heatYear`); it opens on the latest year in the date range, the arrows stop at the range's first/last year, and a date-range change keeps the year if it's still in range. Cells are shaded **linearly** by minutes (`heatColor(v / max)` over `HEAT_STOPS`), where `max` is the busiest day of the shown year, so the scale changes per year; the legend shows five minute values from 0 to that max. Days with no listening are a neutral grey (`HEAT_EMPTY`, the legend's 0 swatch) that is clearly different from the lightest listening shade, so gaps stand out; days outside the date filter are faded (`HEAT_OUTSIDE`). Everything is in plain minutes (`fmtMinutes()`): the per-year statline (total minutes · active days of in-range days · busiest day) and the hover tooltip (date, minutes, and that day's top artist with their minutes, from `heatTopArtists()`, a day → [artist, ms] map built from `DATA.artists[].days` on first hover). No click action (Ansere's version loaded the day into a map walk, which isn't ported).
- **Artist web** (`#artist-web` section, `buildWebGraph()` / `renderArtistWeb()`): d3 force graph linking the top 25/50/75 artists in the date range (`.seg[data-web="count"]`, `webCount`, default 50; 75 stays within the 80 artists `art_sync.py` fetches photos for). "Linked by" (`.seg[data-web="links"]`, `webLinks`) is *Played together* (default: shared listening sessions) or *Similar artists* (Last.fm similarity; disabled when `DATA.lastfm_links` is empty). Spotify's related-artists endpoint is unavailable to new apps, hence Last.fm. Nodes are always coloured by genre (`genreColor()`, shared with the Taste River so a genre has one colour everywhere; grey for no genre, or one plain colour for every node when there are no genres at all), links inside a genre take its colour and links between genres are neutral (`.cross`), and the legend lists genres with node counts. (An earlier version coloured link clusters found by weighted label propagation; it was dropped because the links already show the clusters.) Played together: `build_artist_sessions()` splits plays into sessions at gaps > `GRAPH_SESSION_GAP` (30 min), counting only plays ≥ `GRAPH_MIN_PLAY_MS` (30s) and skipping "Unknown Artist"; each session with 2+ of the top `GRAPH_ARTIST_CAP` (400) artists is emitted as `[day_index, [artist_idx, ...]]` in `DATA.artist_sessions`, where `artist_idx` indexes `DATA.graph_artists` (the 400 names). Pairs need ≥ `WEB_MIN_SHARED` (2) shared sessions in the date range; strength is cosine-normalised (`shared / sqrt(sessA * sessB)`, where `sess` counts in-range sessions with at least one other displayed artist) so heavy-rotation artists don't link to everything. Similar artists: candidates come from `DATA.lastfm_links` with strength = Last.fm match (0–1); the tooltip lists the most similar artists as "% match" (band members' solo acts often show as 100%). Both modes then use the same link selection: every artist keeps its single strongest link, then more are added strongest-first only while **both** ends are under `WEB_LINKS_PER_NODE` (3) — an "either end under the cap" rule let hub artists collect 20+ links. The layout is settled synchronously (`webSim.tick(300)`) then zoom-fitted (`webFit`, also the Reset view button); positions are remembered by name in `webPos` so re-renders keep their shape. Only the top `WEB_LABELS` (15) artists are labelled until highlighted. Hover shows a tooltip; click pins the highlight and opens `#web-panel` with an "Open in Artist Dive" button; clicking the background unpins. There are no usage instructions on the card; `#web-hint` only reports artists hidden for having no links and in-range top artists outside the all-time top 400 (untracked).
- **Taste Map** (`#taste-map` section after Artist Web, `taste*` functions in `dashboard.js`; ported from Ansere's PR #2 and heavily cut down): canvas map of the top `GRAPH_ARTIST_CAP` (400) artists. `tasteLayout()` runs a d3 force simulation once (300 ticks, ~0.4 s) over `DATA.lastfm_links` pruned to each artist's 15 strongest (`pruneLinks()`), plus a weak same-genre chain so genres don't fray apart; link strength is divided by the smaller node degree so hubs don't collapse the map, and short-range repulsion (`distanceMax(150)`) with a firm pull to the centre keeps small, loosely linked clusters from drifting off. The layout doesn't depend on the date range and is computed lazily: `renderTasteMap()` waits on an IntersectionObserver until the section is within 600px of the viewport, so it never blocks page load. The view is fitted to the 1st–99th percentile of positions. Time works like the race: Play/Pause/Replay, a scrubber with date ticks (`renderDateTicks()`, shared with the race), fixed `RACE_PLAY_SECONDS` playback, resting on the latest day. One control, Show (`.seg[data-taste="mode"]`): *All so far* (artists light up at their first play in the range, dot size = minutes so far) or *Last 30 days* (only artists played in the trailing `TASTE_TRAIL_DAYS`, sized by those minutes); unlit artists stay as faint dots. `buildTasteData()` keeps sparse per-artist day/running-total arrays for the range; `tasteCum()` interpolates across a day so dots grow smoothly. Dots use `genreColor()`; genre names are drawn faintly *behind* the dots at each genre's minutes-weighted centre once 3+ of its artists are lit, and the `TASTE_NAMES` (14) biggest lit artists get name labels that skip overlaps. Light theme via `raceColors()`. Wheel zooms about the cursor, drag pans, Reset view restores the fit; hover shows minutes in range, genre and first play. Cut from Ansere's version on purpose: Web Worker + localStorage layout cache (unneeded at 400 artists), genre-anchored layout mode, recency colour modes, label and ghost dropdowns, reactive genre labels, speed dropdown, first-listen pulse rings, glow/trail overlays, dark theme.
